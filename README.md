## 这是什么

一个聊天界面，但对话不是从上往下排成一列，而是散在一张可以自由拖拽的画布上。每条消息是一个节点，节点之间用线连起来，**一个节点可以有多个父节点**。

发送时，程序把当前节点的所有祖先收集起来、拓扑排序成一条消息链，再发给模型。所以画布上是图，发出去的仍然是标准的 `messages` 数组——任何 OpenAI 兼容的服务都能直接用。

## 为什么要做

主流 AI 聊天软件都是线性的，于是有四个绕不开的毛病：

| 问题 | 线性聊天里 | 这里怎么解决 |
| --- | --- | --- |
| **上下文污染**<br>问个岔路问题，主线被带偏 | 只能新开会话，丢掉全部前文 | 从任意节点拉一条分支，岔路和主线互不影响 |
| **分支丢失**<br>重新生成一次，上一版好答案没了 | 直接覆盖 | 「并排重生」保留旧回答，新版本长在旁边 |
| **无法比较**<br>想对比两种思路 | 开两个窗口来回切 | 两条分支并排放在画布上，一眼看完 |
| **无法汇合**<br>A 分支和 B 分支各得到一半结论 | 手动复制粘贴 | 一个节点可以有**多个父节点**，两条分支的结论自动合进同一个上下文 |

**最后一条是关键。** 前三个问题用树形分支就能解决，唯独「汇合」不行——树里每个节点只有一个父节点，两条分支永远碰不到一起。必须上 DAG。

上面那张截图就是这件事：左边问限流算法，右边问缓存失效，两条分支互不干扰地各自展开，最后拖两条线汇进同一个提问节点。这时模型看到的是完整的五条消息，而不需要你把前面的回答复制粘贴一遍。

## 核心机制

画布上是**图**，发给模型的必须是**序列**。中间那层转换在 [`src/lib/context.ts`](src/lib/context.ts)：

1. 从当前节点出发向上收集**全部祖先**——多条路径到达同一个祖先只算一次
2. 对这个子图做**拓扑排序**（Kahn 算法），保证父节点永远排在子节点前面
3. 同时就绪的节点按创建时间择早优先——于是多条分支合并时按真实发生的时间交错，而每条分支内部的因果顺序不被打乱
4. `system` 节点抽出来合并成一条 system 消息，`note` 节点默认跳过，空节点和出错节点跳过

第 4 步里「跳过空节点」有个意外的好处：**首次生成和重新生成走的是同一条代码路径**。重新生成前先把节点内容清空，它就自动把自己排除在上下文之外了，不需要第二套逻辑。

### 上下文永远可见

非线性对话最容易失控的就是「我到底发出去了什么」。所以这是界面上**唯一的强视觉信号**：

选中任意节点，不在它上下文里的节点会整体降透明并去饱和，路径上的连线变成流动的强调色，底部状态条同时报出条数和估算的 token 数。

其余一切都为它让路——节点的操作按钮默认隐藏，悬停或选中才浮现；模型名、token 用量这类元信息同理。画布上放二三十个节点也不会变成按钮墙。

## 功能

**对话**
- 从任意节点分叉，分支之间上下文完全隔离
- 多父节点合并——这是 DAG 而非树的全部意义
- 「并排重生」保留旧回答，在旁边生成新版本；在已有回答的提问上再点发送同样不会覆盖
- 流式输出，可随时停止（已生成的部分保留）
- 推理模型的思维链（`reasoning_content`）单独折叠显示，且不进入下一轮上下文

**节点类型**
- **提问** — 你说的话
- **AI** — 模型的回答
- **系统** — 作为 system 提示注入下游所有分支
- **批注** — 画布上的备忘，默认不进上下文，可勾选让它参与

**画布**
- ⌘K 全文搜索，回车跳转并居中
- 一键分层整理布局（dagre），可撤销
- 折叠整棵下游子树，节点上显示藏了多少个
- 小地图、缩放、框选

**安全网**
- 完整的撤销 / 重做（⌘Z / ⌘⇧Z），覆盖删除、连断线、整理、重生、编辑
- 连续打字和一次拖拽合并成一条历史，不会退一个字符一步
- 删除子树后弹提示告诉你删了几个、可以撤销
- 连线成环会被拒绝并说明原因

**看清上下文**
- 点底部状态条打开预览，逐条列出实际会发出去的 `messages`，每条可溯源到节点
- 单列「在这条路径上、但没发出去的节点」并写明原因
- 任意节点可静音：留在画布上，但不进下游上下文
- 一条路径可导出为 Markdown 对话记录

**公用知识库（RAG）**
- 往画布里拖入文件，**当前画布的所有对话**共用这份资料
- 支持 `.txt` `.md` `.docx` `.epub` 以及常见纯文本（`.json` `.csv` `.html` 源码等）
- 提问时按语义检索最相关的几段，作为「参考资料」附在问题前面发出去
- 命中了哪几段、来自哪个文件、相似度多少，都在上下文预览里逐条列出
- 每个文件可以单独停用，不必删了重建
- 向量服务连不上时**整条请求不发出去并明确报错**，而不是安静地不带资料继续问

**防丢失**
- 自动本地快照，删画布 / 导入 / 回滚前必打点，可整份回滚或只捞回一个画布
- 完整备份包 `.nexus.zip`：画布、设置、**附件原件、知识库资料与向量**一起打包，换台电脑导入就是完整的一套；恢复前先报出包里到底有多少东西，数量对不上账会当场警告
- 导出默认不含任何 API Key（模型的和向量服务的都清掉）
- 导入设置只合并、不覆盖已有配置
- 生成到一半切换画布不会中断，答案继续写回原来那张；切回去时它已经好了

**其他**
- 亮 / 暗双主题，默认跟随系统
- 多套模型配置，不同分支用不同模型横向对比；同一问题的多个回答可并排对比
- 画布导出 / 导入 JSON

## 支持哪些模型

任何实现了 OpenAI `/chat/completions` 协议的服务都能接。设置里内置预设，选一个就自动填好 Base URL：

小米 MiMo · xAI Grok · OpenAI · DeepSeek · OpenRouter · 硅基流动 · Moonshot · 智谱 GLM · 本地 Ollama

也可以手填任意 Base URL。可以存**多套配置**，在不同分支上跑不同模型做横向对比。

> **聊天订阅不等于 API。** SuperGrok、ChatGPT Plus、Claude Pro 这类消费端订阅只能用官方的网页和 App，
> 不含 API 额度，也没法在这里用。要接 Grok 得单独去 [console.x.ai](https://console.x.ai) 申请 API Key，
> 按 token 另行计费。

### CORS 提醒

浏览器直连模型厂商，所以对方必须允许跨域。上面这些都没问题。本地 Ollama 需要启动时加环境变量：

```bash
OLLAMA_ORIGINS=* ollama serve
```

连不上时，「测试连接」会明确告诉你是 CORS、Key 错了、还是 Base URL 写错了，不会只甩一个 `Failed to fetch`。

## 配置知识库

知识库靠一个**向量服务**把文字变成向量来做语义检索，和聊天模型是两回事，要在设置里单独配。
任何实现了 OpenAI `/v1/embeddings` 协议的服务都能接（OpenAI、硅基流动、Ollama……）。

推荐在本地跑，资料一步都不出机器。以 llama.cpp + [bge-m3](https://huggingface.co/BAAI/bge-m3) 为例：

```bash
llama-server -m bge-m3.gguf --embedding --embd-normalize 2 --pooling cls \
  --port 8081 --alias text-embedding-bge-m3 --api-key local-llama
```

设置 → **知识库向量服务** → Base URL 填 `http://localhost:8081/v1`，模型名填 `text-embedding-bge-m3` → **测试连接**。

有三个坑值得单独说：

1. **必须写 `localhost`，不能写 `127.0.0.1`。** https 页面访问 `http://127.0.0.1` 会被浏览器的混合内容策略拦掉，`localhost` 则被当作可信来源放行。填了 IP 设置里会直接提示。
2. **`--embd-normalize 2` 不能省。** 检索用点积代替余弦相似度，靠的就是向量已归一化。建库时会校验，不对会明确报错。
3. **模型文件放在外置硬盘的话，用之前先确认盘挂上了。** 服务起不来时的报错会提醒这一点。

配好之后，顶栏**知识库** → 把文件拖进去。索引完成后，这个画布里的每一次提问都会自动带上检索到的资料。

## 数据与隐私

API Key、画布、设置**全部存在浏览器的 IndexedDB 里**，不经过任何第三方服务器。请求是你的浏览器直连模型厂商的。

在线版也一样——[部署出去的站点](https://yule1048596-art.github.io/nonlinear-chat/)不含任何密钥，每个访问者用自己的 Key，存在各自浏览器里，互不相通。

代价是**清浏览器数据会一起清掉**。重要的东西记得用设置 → 数据 → 「导出全部」打成 `.nexus.zip`，那里面连附件原件和知识库向量都在，换台电脑导进去就是完整的一套。

单个画布也可以导出成 JSON（顶栏 ↓）。导入时会重新分配节点 id，所以同一个 JSON 可以反复导入而不会撞车 —— 但**单画布 JSON 不含附件**，它只是画布结构本身。

## 实现上踩过的坑

这些都是花了时间才定位到的，记下来省得别人再踩：

- **撤销栈存整份快照不等于深拷贝。** store 里每次改动都是 `nodes[id] = {...old}` 整体替换、从不原地改，所以两份快照之间没变的节点是同一个对象引用——一条历史记录只是含 N 个指针的对象。
- **流式输出必须排除在撤销历史之外**，否则每 33ms 一条记录，几秒就把栈冲爆。
- **子树折叠在 DAG 下不能写成「隐藏所有后代」。** 汇合节点可能同时挂在被折叠的分支和另一条可见分支下面，简单藏掉后代等于吞掉一条可见路径的终点。正确做法是从根节点传播可见性：节点可见当且仅当它至少有一个可见且未折叠的父节点。
- **浮层菜单必须 portal 到 body。** React Flow 的 viewport 带 `transform`，会成为 `position: fixed` 的包含块，直接渲染的菜单会定位到错误的地方。
- **React Flow 的双击缩放会 `stopPropagation`**，把 `onDoubleClick` 吃掉。必须 `zoomOnDoubleClick={false}` 才能做「双击建节点」。
- **受控模式下 React Flow 不会把量到的节点尺寸写回你的节点对象**，只通过 `onNodesChange` 的 `dimensions` 变更告诉你一次。小地图判断「节点有没有尺寸」看的正是 `node.measured`，丢了这个变更小地图就一个节点都不画（连线不受影响，它读的是内部测量值）。
- **流式输出时每个 token 都 setState 会拖垮画布。** 两层处理：节点内容更新节流到约 30fps；React Flow 的节点对象按 id 缓存，只有位置/选中态变了才换新对象，内容变化由 `MessageNode` 自己订阅 store 消化。
- **纯防抖存盘在流式输出时永远不会触发**（token 一直在来，计时器一直被重置）。`createDebouncedSaver` 带 `maxWait`，最多攒 3 秒强制落一次盘。
- **页面在流式输出中途被关掉**，节点状态会卡在 `streaming`。加载时统一洗成 `idle`。
- **悬停才出现的操作条必须始终占位**，否则悬停瞬间节点高度变化，连线会跟着抽动。用 `opacity` 而不是 `display`。
- **GitHub Pages 工作流的 `concurrency` 不能用 `cancel-in-progress: true`。** 在真正发布的中途掐断任务，GitHub 会卡在 `updating_pages` 出不来，导致后续所有部署一路轮询到超时。
- **`abort()` 是同步返回的，但被中止请求的 `catch` 分支要到之后的微任务才跑。** 撤销时先 abort 再还原状态，那个迟到的 catch 会把已收到的部分内容写回节点，正好盖掉刚还原的结果——撤销被静默取消。必须区分「用户按停止」（保留已生成部分）和「撤销作废」（一个字都不写回）。
- **删除数据前必须先取消它的待写入。** 防抖存盘里压着刚编辑过的画布，删除后定时器一到又把它写回去，现象是「删了又自己回来了」。
- **摘要压缩空白后，高亮偏移必须在压缩后的字符串上重算。** 先按原文算下标再压缩，前缀里每有一个多余空白高亮就右移一格，实测直接错位到越界。
- **本地向量服务地址必须写 `localhost`，不能写 `127.0.0.1`。** 部署在 https 上的页面访问 `http://127.0.0.1` 会被浏览器的混合内容策略拦掉，而 `localhost` 属于「潜在可信来源」不受此限。同一个服务、同一个端口，换个写法就是通与不通的区别。设置里填了 IP 会直接给出提示。
- **检索用点积代替余弦相似度，前提是向量已 L2 归一化。** llama.cpp 要加 `--embd-normalize 2`，改了这个参数点积就不再等于余弦，排序会悄悄失真。建库时会校验第一批向量的模长，不对就明确报错而不是给出错的结果。
- **不要用相似度阈值过滤检索结果。** 实测 bge-m3 上「两个相关技术话题」和「技术 vs 完全无关话题」的分差只有 0.07 左右（0.651 vs 0.584），任何绝对阈值都会一刀切错。这里的做法是如实把分数显示在预览面板里，由人判断这次检索准不准。
- **知识库检索失败时宁可整条请求不发，也不要不带资料继续问。** 用户明明往画布里加了资料，答案却是凭空编的——这种「看起来正常其实没读资料」比直接报错难发现得多。
- **`.epub` 的章节顺序要按 OPF 的 spine 读，不能按 zip 里的文件顺序。** 后者经常是乱的，直接拼出来的正文会前后错乱。
